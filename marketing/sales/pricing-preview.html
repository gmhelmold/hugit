A cunha

Landing, não autoria

O gargalo de uma fleet de agentes não é escrever código — é integrar e mergear o que dezenas produzem ao mesmo tempo, sem quebrar a main. hugit é a fila que faz isso por union-testing.

  • ✓ main tem um escritor só (a fila) — nunca vira bagunça concorrente
  • ✓ Branches sincronizam dos dois lados, seamless
  • ✓ Force-push recomputa; kill-tests barram regressão
O motor

CI que não re-roda

Cada check é memoizado por conteúdo no Action Cache. Já rodou esse exato estado ⇒ resultado instantâneo, custo zero. Você paga plano flat, não por minuto — e nunca pelo seu próprio compute.

  • ✓ Cache-hit ⇒ 0 execução (< 500 ms)
  • ✓ Só roda o que o diff realmente afeta
  • ✓ Hit-rate honesto — não inflamos número

A família HuGR

Uma pilha só: HuGR (a casa) → CoreLink (a plataforma) → hugit (o forge, em cima). Mesmo cache content-addressed por baixo de tudo.

◆ CoreLink Cache Launch
A base: cache + governança de storage. CAS, Bazel, Turborepo, sccache, adapters. hugit consome — não reimplementa.
⚡ CoreLink Runners Fase 3
Compute efêmero sobre o cache. É onde os checks do hugit executam (quando não dá cache-hit).
⬡ CoreLink Workspaces Fase 3+
Workspace como objeto. Os sandboxes/fences de agente do hugit são SKUs deste primitivo.
⑂ hugit Você está aqui
O forge LLM-native (campanha #3): landing + merge + CI memoizado pra fleets. Construído sobre o CoreLink; cobrado como um produto só.

Um produto, uma fatura: o cliente do hugit vê só o hugit. CAS / Action Cache / runners do CoreLink são a base por baixo (COGS), nunca uma linha separada na conta — porque hugit é CoreLink, da HuGR. · Preço flat, memoizado: nunca cobramos pra re-rodar o que está no cache, nem pelo seu próprio compute.

Preços em USD, indicativos — validar contra o COGS (consumo de CAS/AC/runners do CoreLink, por tenant, com teto de política) antes de publicar. Execução ao vivo depende do provisionamento do tenant CoreLink (P2) — lança junto com a base.
