# Research — git core pains + next-gen VCS landscape

> Lane 1 of the 4-agent evidence sweep behind the founding brief.
> Researched 2026-06-05 (Opus web-research agent). Citations inline.

## Top pains (ranked)

1. **Merge conflicts in generated/lockfiles** — felt by every team using npm/yarn/pnpm/Cargo. A lockfile produces "dozens of conflicts for every single conflict in package.json," and resolution is "highly inefficient and error-prone" because the file is generated, not authored — deleting + re-running yields a different tree, so "your app may or may not be fine, no one can tell" ([tkdodo.eu](https://tkdodo.eu/blog/solving-conflicts-in-package-lock-json), [dev.to](https://dev.to/cloudx/resolving-git-conflicts-in-package-lockjson-using-a-merge-driver-2ipk)). Whole tools exist purely to paper over this (`npm-merge-driver`). **Severity: high, daily, universal.** Textual diff over machine-generated/semantically-disjoint content is the root cause.

2. **Rebase / history-editing footguns** — felt by intermediate devs and especially anyone editing shared history. Force-push after a tidy rebase "only to realize you've mistakenly dropped commits containing hours of work"; detached-HEAD orphans commits; recovery requires reflog spelunking ([blog.edwardsmatt.com](https://blog.edwardsmatt.com/posts/recovering-from-a-git-force-push/), [oneuptime.com](https://oneuptime.com/blog/post/2026-01-24-git-detached-head-state/view)). The existence of mature "bring commits back from the dead" guides is itself a frequency signal. **Severity: high, recurring.**

3. **CLI/UX confusion & the staging area** — broad/beginner. The single most-cited jj selling point is that it *removes* git's pain surface: no staging area / `git add`, universal `jj undo`, no detached-HEAD class of errors ([kunalganglani.com](https://www.kunalganglani.com/blog/jujutsu-jj-git-version-control), [swiftwithmajid.com](https://swiftwithmajid.com/2025/10/15/introducing-jujutsu-vcs/)). The fact that the fastest-growing alternative's headline value is "better interface to the same data model" is the strongest signal that git's UX is the pain.

4. **Large-file handling (LFS hate)** — game/ML/asset teams. LFS has "high vendor lock-in," is "impossible to undo without rewriting history," makes "identical git commands behave differently," and is 3× costlier than raw S3 ($40 vs $13/yr for 50GB) ([tylercipriani.com](https://tylercipriani.com/blog/2025/08/15/git-lfs/), [stackshare LFS alternatives](https://stackshare.io/git-lfs/alternatives)). Git's own answer — *large object promisors* — only began merging Mar 2025 and is incomplete, confirming the gap is real and unsolved upstream. **Severity: high for a specific, high-value segment.**

5. **Monorepo scale** — large orgs. `git status`/`checkout` "slow to a crawl" with many files; partial-clone + sparse-checkout are the workarounds but are themselves painful to operate ([github.blog sparse-checkout](https://github.blog/open-source/git/bring-your-monorepo-down-to-size-with-sparse-checkout/), [docs.gitlab.com monorepos](https://docs.gitlab.com/user/project/repository/monorepos/)). jj's lazy backend is explicitly designed for this ([lwn.net 958468](https://lwn.net/Articles/958468/)). **Severity: high but concentrated.**

6. **Worktrees + concurrency (the agent-era pain)** — teams running parallel AI agents. Worktrees are "the secret weapon" for parallel agents but git "is not designed for concurrent operations"; simultaneous commands on shared repo data can corrupt, and submodule interaction is broken (force-removal, manual moves, duplicated disk) ([upsun](https://developer.upsun.com/posts/ai/git-worktrees-for-parallel-ai-coding-agents), [biggo.com](https://biggo.com/news/202508090812_Git_Worktrees_Storage_Challenges)). **Severity: rising fast — this is the net-new 2025-26 pain.**

7. **Submodules** — anyone with vendored deps. Universally cited as awkward; worse under worktrees (each worktree needs own init). **Severity: medium, chronic.**

## Next-gen VCS landscape

- **Jujutsu (jj)** — *Thesis:* same git data model, radically better interface; first-class conflicts (a conflict is stored, not blocking — markers only materialize if you check out the conflicted commit), automatic descendant rebase, universal undo, no staging area. *Momentum:* 27k+ GitHub stars, full-time Google project, Martin von Zweigbergk paid by Google, used internally, 39c3 talk Dec 2025, heavy 2025-26 blog/HN volume ([github.com/jj-vcs/jj](https://github.com/jj-vcs/jj), [lwn 958468](https://lwn.net/Articles/958468/), [HN 45759572 "Jujutsu at Google"](https://news.ycombinator.com/item?id=45759572)). *Forge story:* deliberately *none yet* — reuses any git forge; roadmap adds `jj github/gitlab/gerrit submit`; `change-id` header enables better review *if the forge supports it* ([docs.jj-vcs.dev/github](https://docs.jj-vcs.dev/latest/github/)). **This is the open lane — jj has no native forge.** *AI relevance:* first-class conflicts + auto-rebase + undo map almost perfectly onto agent workflows (non-blocking conflicts, cheap branch exploration).
- **Sapling (Meta)** — *Thesis:* user-friendly + scalable, stacked diffs as a first-class everyday pattern, rich undo. *Momentum:* open-sourced 2022, "has not gained significant traction outside Meta"; advanced features need a *proprietary server not publicly released* ([engineering.fb.com](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/), [Medium/Neighbour](https://medium.com/@benneighbour/is-metas-sapling-the-future-of-vcs-3d106fcebce0)). *Forge story:* tied to Meta's internal server → external dead-end. *AI relevance:* stacked-diff model fits agent micro-commits, but closed server kills it as a base.
- **Pijul** — *Thesis:* patch/change-based (not snapshot), commutative patches = a CRDT; merge is mathematically a pushout, so order-independence eliminates whole conflict classes (rebase A-onto-B ≡ B-onto-A) ([pijul.org/manual/why_pijul](https://pijul.org/manual/why_pijul.html)). *Momentum:* small; weak ecosystem (no bisect, few GUIs, tiny hosting). *Forge:* Nest (own host), niche. *AI relevance:* the *theory* is the most agent-friendly (commutative, conflict-light), but maturity is low — a model to borrow, not adopt.
- **Fossil** — integrated VCS+wiki+tickets+forum, single-binary; niche (SQLite community). Not an agent play.
- **AgentGit (arxiv 2511.00628, Nov 2025)** — not a VCS for code but git-*style* version control over *agent runtime trajectories* (commit/revert/branch agent state); beats LangGraph/AutoGen/Agno, cuts redundant compute + tokens ([arxiv](https://arxiv.org/abs/2511.00628)). Signal: the version-control *metaphor* is being pulled up into the agent layer.

## Semantic merge SOTA

- **Exists:** **Mergiraf** — Tree-sitter/AST-aware git *merge driver* (drop-in for merge/rebase/cherry-pick), v0.4 added Python/TOML/TypeScript/Scala; auto-resolves structurally, leaves clear markers when unsafe ([mergiraf.org](https://mergiraf.org/), [HN 42093756](https://news.ycombinator.com/item?id=42093756)). **difftastic** = structural *diff* only, no merge ([github.com/Wilfred/difftastic](https://github.com/Wilfred/difftastic)). **LLM/ML approaches:** ChatMerge / strategy-classification + LLM ([IEEE 10366637](https://ieeexplore.ieee.org/document/10366637/)); **ConGra** benchmark (44,948 conflicts / 34 projects) ([arxiv 2409.14121](https://arxiv.org/abs/2409.14121)); **LLMinus** ([lwn 1051607](https://lwn.net/Articles/1051607/)). Finding: longer-context ≠ better; general LLMs beat code-specialized LLMs at resolution.
- **Missing:** (a) no standard *semantic-diff-aware storage* — merge tools bolt onto git's line model post-hoc; (b) **no good story for generated/lockfile conflicts** (the #1 pain) — AST merge doesn't help a regenerated tree; (c) no benchmark/grading of conflict difficulty in production; (d) LLM resolution is research-grade, not productized into forges; (e) nothing combines semantic merge + first-class (jj-style) conflicts + LLM fallback.

## Git-protocol-over-alternative-storage feasibility

**Proven prior art:**
- **libgit2 ODB backends** — git's object DB is pluggable; backends exist for non-filesystem stores (packed binary, DB, cold-storage) ([libgit2/libgit2-backends](https://github.com/libgit2/libgit2-backends), [Perforce pluggable-backends](https://www.perforce.com/blog/your-git-repository-database-pluggable-backends-libgit2)). Refs backend is also pluggable.
- **GitHub Spokes/DGit** — production: git served at app layer over 3 loosely-coupled replicas, every object indexed by content hash; "no SAN, no distributed FS" — pure app-level git over commodity storage ([github.blog DGit](https://github.blog/engineering/architecture-optimization/introducing-dgit/), [infoq Spokes](https://www.infoq.com/news/2017/10/github-spokes-replication/)). **GitLab Gitaly** = RPC layer abstracting repo storage in production ([dev.to Gitaly/Scalingo](https://dev.to/etiennem/gitaly-at-scalingo-explaining-the-complete-redesign-of-how-we-host-your-application-git-repositories-4550)).
- **Object-store as git remote** — `awslabs/git-remote-s3` and others make S3 a serverless git remote; **R2 is S3-API-compatible with zero egress** ([awslabs/git-remote-s3](https://github.com/awslabs/git-remote-s3), [josephvoss.com](https://josephvoss.com/post/git-remote-s3/), [Cloudflare R2 S3 docs](https://developers.cloudflare.com/r2/get-started/s3/)). Caveat: bucket-level auth loses granular RBAC — push it up into your service layer.

**Verdict: HIGHLY FEASIBLE and battle-tested.** Git's content-addressed object model maps cleanly onto any CAS; the two big forges already serve the git protocol from app-level stores indexed by content hash — exactly the shape of a multi-tenant R2-backed CAS. The work is the protocol-v2 server + smart-HTTP/pack negotiation over your CAS, not novel research. The remote-helper route is a quick MVP; a real pack-aware protocol-v2 server is the durable build.

## Implications for an LLM-native forge

- **Lead with git-protocol compatibility, not a new client.** jj's entire growth proves "keep your git/GitHub/CI, swap the layer underneath" is the only adoption path that works. Serve the git wire protocol from your R2 CAS so existing clients (and agents using plain git) just work; this is proven by Spokes/Gitaly/git-remote-s3.
- **Make conflicts first-class (jj's killer feature) at the storage layer.** Store conflicted states as objects, don't block on them — this is exactly what parallel-agent fleets need (non-blocking, explorable trajectories). jj validates the model; no forge offers it server-side.
- **Own the #1 pain git's wave hasn't solved: generated/lockfile conflicts.** Register semantic/regeneration-aware merge drivers server-side (Mergiraf-style AST for code; "regenerate, don't textual-merge" for lockfiles) so conflicts auto-resolve before a human/agent ever sees them. This is differentiated and high-frequency.
- **Productize LLM-assisted merge** as a server feature with a confidence gate (research = ChatMerge/ConGra/LLMinus; none shipped in a forge). You're an LLM-native platform — close the gap research left open.
- **Native large-file handling kills LFS.** Content-addressed R2 storage *is* the large-object-promisor design git is slowly bolting on (merged Mar 2025, incomplete). Offer transparent large blobs, zero egress, no pointer files, no vendor-lock rewrite — directly attacking documented LFS hate.
- **Branches → sessions: capture intent, not just diffs.** Piñera's thesis — record prompt/reasoning/tests/feedback as first-class artifacts ([pepicrft.me](https://pepicrft.me/blog/rethinking-version-control-for-agents/)). A CAS naturally stores these as addressable objects linked to commits.
- **Design for concurrency from day one.** Git "is not designed for concurrent operations" and corrupts under parallel agents; a multi-tenant CAS with atomic ref updates structurally fixes the worktree/shared-index corruption pain.
- **Cheap, abundant branches/snapshots are the agent primitive** (AgentGit, "hundreds of micro-commits in seconds"). CAS dedup makes 1000 agent branches nearly free — a moat git's filesystem model can't match.
- **Forge-side review for change-ids / stacked diffs.** jj emits a `change-id` header but most forges ignore it; supporting it natively wins the entire jj community as your front-end while you own the backend.
- **Wedge: serve jj *and* git over the same CAS.** jj has 27k stars and explicitly *no native forge* — that is the single clearest unmet demand in this space. Be the forge jj doesn't have, with semantic merge + LLM resolution + zero-egress large files as the paid surface.
