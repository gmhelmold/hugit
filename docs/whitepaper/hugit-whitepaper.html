HuGR · CoreLink · campanha #3

hugit

Version control e forge LLM-native. Uma inversão: versione o intent, o contexto e a prova — e trate o diff de código como a projeção verificada deles. git nunca é quebrado; o que vive em cima dele é nativo de fleets de agentes.

Software em 2026 já é escrito por fleets de agentes sob comando humano. A stack embaixo — git + GitHub — foi feita pra outra espécie de trabalhador: humanos, no ritmo humano, com memória humana. O resultado é uma crise de integração mensurável. hugit ataca a causa raiz.

01O problema, medido

27.67%

A autoria virou commodity. O gargalo migrou pra pousar com segurança (merge + CI + review) o que os agentes produzem em paralelo — e pra recuperar o entendimento que o git joga fora a cada sessão. Toda sessão de agente termina numa "rodada de reconciliação", re-pagando pelo contexto que a ferramenta descartou. O review humano (LGTM) virou o gargalo de toda a máquina; reviewer LLM lendo diff cru acerta só 24–46%.

02A inversão (a tese)

O git fez do código a fonte da verdade e jogou o intent fora — a troca certa em 2005. O hugit faz de intent + contexto + prova a verdade versionada, e trata o código como projeção verificada deles.

E uma invariante acima de tudo: git nunca é quebrado. Todo repo hugit é, a qualquer instante, um repo git válido no protocolo padrão. Se toda camada inteligente cair, sobra git rápido e saudável.

03O xeque-mate econômico

hugit é a camada 4 do CoreLink — plataforma de storage e computação content-addressed já em produção. Isso dá uma propriedade que o incumbente não copia sem destruir a própria receita: os custos que dominam um forge — compute de CI, storage, egress, setup de ambiente — são memoizados, deduplicados ou zero-rated por construção.

GitHub fatura o desperdício

CI por minuto (re-roda tudo), AI usage-billed (choques de 10–50×), egress por byte. O desperdício é a receita — então não pode ser removido.

CoreLink deleta o desperdício

Verificação memoizada por conteúdo, dedup global, egress R2 = $0, ambiente hidratado de cache quente. Margem da empresa e velocidade do cliente são o mesmo número.

Não é guerra de features — é guerra de incentivos, e os incentivos do incumbente estão do nosso lado. E aprofunda com escala: artefatos public-deterministic de cada tenant aquecem o cache de todos; o cliente #500 chega num workspace já ~40–70% quente. O produto melhora conforme cresce. (Fronteira inegociável: público-determinístico compartilha; bytes privados nunca cruzam tenants.)

04O prêmio de consolidação & o TAM

Um dev agent-heavy hoje paga $200–600/mês fragmentado entre GitHub + agentes Copilot + runners + stacked-PR + AI review + sandboxes. hugit é uma fatura só, flat e previsível. Doutrina de preço: flat por unidade-que-escala (assentos de orchestrator, runners paralelos, workspaces quentes); nunca medir o compute do próprio cliente; nunca usage-whiplash.

TAM de ferramentas de código IA: $9.5B (2026) → $22B (2030). Mas a tese mais funda: a categoria do hugit não é "ferramenta de código" — é o sistema de registro do software construído por máquinas. A camada onde todo o resto se pluga.

05O moat & a janela

  • A pilha se compõe: HuGR → CoreLink (cache → compute → workspaces) → hugit (forge). Cada camada reforça a de baixo; ninguém sem cache content-addressed em escala precifica isso.
  • Abraça, não ataca: a fase 1 roda sobre o GitHub — zero migração. Velocidade vence completude; entramos rápido porque L0–L2 já existem.
  • O moat social não é nosso pra ganhar — ganhamos o workflow; as estrelas ficam onde estão até a comunidade movê-las.
a tese em uma linha

git foi a revolução do desenvolvimento dirigido por humanos. hugit é a revolução do desenvolvimento dirigido por LLM — com humanos no comando.

Seu enxame de agentes tá cuspindo PR sem parar. Massa. Só que o git **joga fora o cérebro** que produziu cada mudança, e ninguém tá juntando isso sem explodir a main. hugit versiona o intent + o contexto + a prova — não só o texto. Você vibe; ele lembra, junta e pousa.

01O inferno que sobrou

A IA já escreve o código. O que sobrou pra você: 30 PRs "prontos", dois mexeram no mesmo arquivo, um quebrou a main, o CI rodou o mesmo teste 200× hoje (💸), e o contexto do agente — o porquê de cada decisão — evaporou quando a janela fechou. Aí você re-explica tudo no próximo merge. 💀

O git versiona o texto e esquece o entendimento. Em time humano isso ficava na cabeça das pessoas. Numa fleet de agentes, some com a context window — e você re-paga toda vez.

02O que o hugit guarda por você

  • O contexto viaja com o trabalho. Modelo, arquivos lidos, tool calls, o raciocínio (redactado por política) — vira um snapshot versionado anexado ao intent. Dá pra resumir, dar replay, auditar — em vez de re-explicar do zero.
  • Conflito é pego ANTES de você começar. Cada trabalho declara o que vai tocar (claims). Dois agentes na mesma coisa? O sistema avisa no dispatch, não às 2h da manhã no merge.
  • A main é sagrada. Ninguém empurra direto. Uma fila testa os PRs juntos e pousa em ordem — acabou o "passou sozinho, quebrou junto".
  • CI que não repete. Já rodou esse estado exato? Verde na hora, custo zero.

03Coisas que vão te fazer sorrir

🧠 Contexto versionado

O "porquê" de cada mudança fica salvo e resumível. Sessão nova começa quente.

🔀 Merge que re-executa

Em vez de brigar com patch de texto, ele re-roda o intent na base nova. Trabalho ortogonal pousa limpo.

💬 Interroga a mudança

"Onde isso toca o fluxo de dinheiro?" "Me convence que é seguro." Resposta do intent + contexto + evidência, com link até a linha.

↩️ Undo de tudo

Tudo é evento. Force-push que apaga histórico? Nem existe — é inexprimível aqui.

04E o melhor: zero amarra

Roda em cima do teu GitHub — zero migração, sincroniza nos dois sentidos. A árvore de arquivos é só uma árvore de arquivos (local, web, ou no mirror do GitHub). Quis sair? Leva tudo, com prova de export. Preço fixo, sem medidor por minuto, e você nunca paga pra re-rodar o que já rodou.

Solta os agentes. O hugit lembra o contexto, pega conflito antes da hora, testa junto, mantém a main verde, e te cobra uma vez. Você só vibe. 🚀

hugit versiona um modelo de objetos content-addressed (Intent, Context Snapshot, Trajectory, Claim, Verdict, Check Result) sobre a CAS do CoreLink; os objetos do git são preservados byte-exatos como projeção. Estado mutável (refs, filas, políticas) é um namespace event-sourced fino por cima. 14 crates Rust, oracle-first, mutation-verified.

01O object model

objetoessência
Intent{id, campaign, charter, constraints, acceptance[], claims, parent_intents[], ctx_start, trajectory, diff_ref, evidence[], verdicts[], state}
Context Snapshot{model, charter_ref, files_read[(path,hash)], tool_calls[], conversation_ref (redacted per policy), journal_ref, env_manifest} — hoje: destruído
Trajectoryevent log append-only da execução de um intent; replayable, time-travelable
Claim{paths[], build_targets[], contracts[]} — declarado no plan, imposto fisicamente
Workspacesource+deps+toolchain+build-state como um manifest; materializado por claims; local≡remoto
Verdict{intent, tree_hash, lens, verdict∈{APPROVE,FIX-FIRST,REJECT}, claims_checked[], evidence[]}
Check Resultmemo de check(tree_hash, def_digest, toolchain_digest)
Blob/Tree/Commitobjetos do git, byte-exatos — a projeção

Projection rule: todo intent que pousa emite commits git determinísticos (mensagem gerada embutindo o intent_id). git log é a altitude-máquina; hugit log é a altitude-intent. Mesma store, dois zooms — nunca discordam porque um é derivado do outro. (O sidecar de intent — IntentSidecar.context_ref — já está construído no crate hugit-app-sidecar, não-autoritativo por design; o verbo ctx snap/resume está reservado.)

02Claims & conflito-no-dispatch

claims(I) = fecho sobre o build-graph de {paths ∪ targets ∪ contracts}
independent(I,J) ⇔ claims(I) ∩ claims(J) = ∅
plan(P): pares na wave se intersectam? planner re-slice ou adiciona aresta no DAG
runtime: workspace materializa SÓ claims(I) — escrita fora é fisicamente
         impossível (o arquivo não está lá) + evento de política

Conflitos verdadeiros aparecem antes do trabalho começar. Overlap textual dentro de claims compartilhadas emite evento aos dois orchestrators em segundos. A fence é a materialização esparsa — rm -rf não tem pra onde ir.

03Checks puros, memoizados

key = H(tree_root ‖ check_def_digest ‖ toolchain_digest)
check(key) → AC hit? retorna prova : executa no runner, armazena, retorna
affected(Δtree) = conjunto de checks alcançável no build-graph
shadow: a cada snapshot de workspace, avalia affected(Δ) especulativamente

hugit check local e a execução no forge são a mesma função — byte-idêntica por construção. Byte-identity é load-bearing: mesmo input ⇒ mesmo CheckResult, ou a memoização envenena; não-determinismo é detectado (difere após 3), não memoizado como verdade.

04Merge como re-execução (regenerative rebase)

rebase(I, base B0→B1):
  se claims(I) ∩ Δ(B0,B1) = ∅:   fast-path textual (limpo garantido)
  senão:
    re-executa I: agent(ctx_start(I), charter(I)) em workspace(B1) → diff D′
    exige acceptance(I) verde em B1+D′
    se distance(D,D′) > policy.threshold → re-verdict
    pousa como nova revisão do MESMO intent (ambas guardadas, endereçáveis)

Re-executar a fonte (o intent, mais barato) em vez de remendar o texto é o default pra trabalho ortogonal — viável porque build/test batem na AC e re-verificar é quase-grátis. Confiança vai de opt-in → default conforme dados de confiança-de-aceitação acumulam.

05Landing — union testing em escala de fleet

queue = intents landable, ordenados por DAG
batch B: U = fold(regen-rebase, head, B)
roda affected checks em U          # quase tudo AC hit — só a novidade executa
verde → pousa o batch atômico (um move de ref no event-log; main sempre verde)
vermelho → bisect sobre checks memoizados (≈grátis) → par mínimo que falha
           → UNION-FAIL estruturado ao owner intent; resto do batch segue
intents de claims disjuntas pousam em lanes paralelas

É o blueprint do SubmitQueue (Uber) com dois upgrades que ele não tinha: claims declaradas à frente (busca dirigida, não descoberta) e verificação memoizada (union test custa só a novidade). A main é single-writer por construção = a fila; o sync com o GitHub é arbitrado pelo forge (branches seamless dos dois lados, idempotente por content-hash, divergência arbitrada nunca dropada — não existe estado de autoridade simétrica pra main).

06Event log & undo universal

Um Durable Object por repo possui um event-log append-only, hash-chained. Refs são view derivada. Toda operação — landing, mudança de política, move de ref — é um evento; hugit undo anexa um evento compensatório. Nada é reescrito; a história é re-projetada. Perda de dados por force-push não é "protegida" — é inexprimível.

07Segurança (5 fechaduras + a fronteira) & proveniência

  • Claims como fences físicas — workspaces capability-scoped; o blast-radius É a claim.
  • Segredos nunca entram no workspace — um broker executa por conta (modelo write-only do CoreLink); agentes não veem credencial.
  • Tudo event-sourced → undo universal — toda ação de todo principal, atribuível e reversível.
  • Policy gates fail-closed — testáveis localmente, impostos identicamente.
  • Invariante de degradação — camadas inteligentes caem ⇒ um repo git válido segue servindo.

Proveniência: todo artefato traça pra {tree_hash, check_def, runner, model, prompt, principal_chain} — atestação classe-SLSA cai do object model, incluindo a camada que o GitHub não expressa: qual modelo escreveu isto, sob instrução de quem, a que custo. Snapshots de contexto são tenant-private, redactáveis, retention-bound, e nunca viram training data.
