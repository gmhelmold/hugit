hugit

O forge git-compatível e LLM-native: resolve o problema de landing — integrar e mergear o que fleets de agentes produzem em paralelo — com CI memoizado por conteúdo. Roda sobre o GitHub, sem lock-in.

IA escreve código mais rápido do que os times conseguem integrar. O gargalo deixou de ser escrever — virou pousar com segurança (merge + CI) o que dezenas de agentes produzem ao mesmo tempo. hugit é o forge que resolve esse gargalo.

01A mudança

Fleets de agentes de código já são realidade. Um time pequeno hoje dispara dezenas de PRs por dia. A autoria virou commodity. O que não escala é a integração: quem mergeia tudo isso sem quebrar a main? Quem roda o CI dessas centenas de execuções sem o custo explodir? Quem decide o que precisa de olhar humano?

A autoria foi resolvida pela IA. A pousada (landing) não. Esse é o gargalo — e a cunha do hugit.

02O que é o hugit

Um forge (hospedagem + merge + CI) desenhado pra fleets de agentes, que roda sobre o GitHub — não substitui, não exige migração, não prende. Ele recebe o que os agentes produzem e pousa com segurança: testa os PRs juntos antes de integrar, mantém a main intocável, e só chama o humano quando realmente precisa.

03Por que ganha

  • Abraça, não ataca. Vive em cima do GitHub que o time já usa. Adoção sem rip-and-replace; saída a qualquer hora com o histórico completo (anti-lock-in é uma feature, não promessa).
  • CI que não re-roda. Cada verificação é memoizada por conteúdo: já rodou aquele estado exato ⇒ resultado instantâneo, custo zero. Numa fleet que roda CI centenas de vezes/dia, o custo de compute despenca.
  • Construído sobre o moat do CoreLink. hugit é a camada 3 da pilha HuGR. O cache content-addressed do CoreLink — o ativo defensável — é o que torna o CI barato e rápido. Ninguém sem esse cache replica a economia.

HuGR (empresa) → CoreLink (plataforma) → hugit (o forge)

04Modelo de negócio

Preço flat, memoizado por conteúdo. Nunca cobramos pra re-rodar o que já está no cache, nem pelo compute do próprio cliente — zero "usage whiplash". Uma fatura só: o cliente vê o hugit; o cache/compute do CoreLink por baixo é base invisível (COGS). Cobrança por repos + assentos + agentes simultâneos (a métrica que é a cara do produto), não por minuto.

05Por que agora

As fleets chegaram; o merge manual e o CI por-minuto não foram feitos pra elas. A janela é a transição: quem virar o forge-padrão das fleets de agentes captura o fluxo de integração — o ponto de maior alavancagem do ciclo de software.

06O moat

A pilha se compõe: cache (CoreLink) → compute (Runners) → forge (hugit). Cada camada reforça a de baixo. O CI memoizado do hugit gera valor que nenhum concorrente sem cache content-addressed em escala consegue precificar. É uma vantagem que aprofunda com escala.

tldr

Solta os agentes. O hugit junta tudo, testa junto, não quebra a main, e não te cobra duas vezes. Você só vibe. 🚀

hugit é um forge git-compatível onde a main tem um único escritor por construção (a fila de landing), o CI é memoização por conteúdo na Action Cache, e o espelho com o GitHub é arbitrado pelo forge — nunca um sync simétrico ingênuo. Workspace Rust de 14 crates, oracle-first, mutation-verified.

01Single-writer main — a física do conflito evapora

"Dois agentes mexem na mesma coisa ao mesmo tempo" só é um problema porque dois escritores disputam o mesmo ref. hugit remove a disputa: ninguém escreve a main direto. O único escritor é a fila de landing (o árbitro). Branches são refs independentes — coexistem, sincronizam nos dois sentidos, zero conflito. O recurso contendido (a main) passa a ter escritor único; a "física de escrita concorrente" some.

02Union-testing landing

  • Um lote de PRs é testado combinado (union tree) antes de pousar — pega a regressão que só aparece quando duas mudanças se encontram (o "passou isolado, quebrou junto").
  • Stale-head recompute: um force-push invalida e recomputa; a fila aplica em ordem total, idempotente.
  • Kill-tests barram a integração de um lote que regride.

03CI = memoização por conteúdo

Cada check tem uma memo key de três eixos:

memo_key = H( tree_hash ‖ check_def_digest ‖ toolchain_digest )
  • Hit na Action Cache ⇒ 0 execução — o resultado volta do cache em <500ms. A maioria dos checks de uma fleet é hit.
  • Byte-identity é load-bearing: o mesmo CheckDef sobre os mesmos inputs produz um CheckResult byte-idêntico, ou a memoização envenena. Não-determinismo é detectado (difere após 3 execuções) em vez de memoizado como verdade.
  • Affected-targets: só roda o que o diff realmente afeta. Hit-rate reportado é honesto, não inflado.

04Sync bidirecional arbitrado pelo forge

Supera o "mirror simétrico ingênuo" (perigoso). Regras:

  • Branches sincronizam dos dois lados, seamless — uma mudança no lado GitHub entra como change-event externo (nunca um intent fabricado, nunca toca a main); uma mudança no forge espelha pra fora.
  • main é single-writer = o forge. Um push direto na main do lado GitHub não é aplicado simetricamente — é re-roteado (branch/PR proposto) pra pousar pela fila.
  • Idempotente por content-hash — sem echo loop; convergiu, o sync silencia.
  • Divergência arbitrada: tips incompatíveis no mesmo branch ⇒ o forge é autoritativo, o tip do GitHub é preservado como incidente recuperável — nunca dropado em silêncio, cadeia sempre verificável.
  • Propriedade: não existe estado alcançável onde os dois lados são autoritativos pra main ao mesmo tempo.

05Execução isolada (compute não-confiável)

  • Fences esparsas por claim: o job só lê/escreve os paths reivindicados; injeção de path absoluto, escape .. e colisão de prefixo (srcfoo vs src/) são todos negados, fail-closed.
  • Isolamento de tenant via prefixos HMAC (herdado do CoreLink), fail-closed; cross-tenant impossível.
  • Secrets broker write-only: o segredo entra no job sem nunca persistir na box (env=0/proc=0/disk=0, atestado; fail-closed em scan inválido).
  • Boot cache-warm e microVM efêmera (executa nos CoreLink Runners; o crate hugit-runner é o cliente).

06Proveniência, atestação & saída

  • Attestation chain + transparency log (ed25519 + boot self-verify): tudo que rodou é assinado; um resultado sem atestação válida é rejeitado.
  • why / impact: proveniência por linha/símbolo e raio de impacto no build-graph.
  • Anti-lock-in real: export + provas de saída; cascata de erasure (right-to-erasure across stores, sem órfãos, tombstones tamper-evident). Você sai com tudo, verificável.

07Fundação

Construído sobre o CoreLink (CAS/AC/runners consumidos, nunca forkados). 14 crates Rust, gates fmt + clippy --workspace --all-targets --locked -D warnings + test --locked + audit. Disciplina: oracle-first, mutation-verified — derrotar uma invariante deixa o teste vermelho, prova que ela é load-bearing, não decorativa.
