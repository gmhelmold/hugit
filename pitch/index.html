A tese · para a sala toda

A dor de 2026 não é escrever código.
É pousar código.

Agents tornaram barato produzir trabalho sobreposto — e caríssimo reconciliá-lo. "A verde. B verde. A+B vermelho." Os orquestradores isolam a execução e param na fronteira do merge. O git não foi desenhado para concorrência; o GitHub não foi desenhado para atores-máquina. Quem resolver o landing problem fica com a camada mais valiosa do novo stack.

🧠

O repo que se explica

Índice semântico vivo, memoizado por tree-hash. Leitura em qualquer altitude. Dispatch packet de contexto gerado pelo forge: despachar um agent = entregar 1 URL.

🟢

Verdade ambiente

Shadow-checks especulativos a cada escrita. Falha chega como diagnóstico (culpado auto-bisectado, diff-vs-verde), nunca como 4.000 linhas de log.

🔀

Merge contínuo

Conflito detectado na escrita, não no merge. União das branches testada especulativamente. Lockfiles regenerados, nunca text-merged. Main sempre verde.

♻️

CI que nunca se repete

Check = função memoizada do tree-hash. Re-verificar o já-verificado vira estruturalmente impossível. O que o cliente ama (velocidade) corta nosso custo.

1 · Nada aqui é pesquisa. É engenharia com arte prévia em produção.

git sobre CAS

O próprio GitHub já faz

Spokes/DGit serve git da camada de aplicação, objetos indexados por content-hash, sem FS distribuído. GitLab Gitaly abstrai storage em produção. libgit2 tem ODB e refs plugáveis. Servir o wire-protocol de um CAS R2 é o MESMO formato de problema — resolvido duas vezes em escala planetária.

CI memoizada

Provada em escala Google/Uber

Bazel action cache + TAP: resultado de check chaveado por hash de inputs, há uma década. Uber SubmitQueue (EuroSys'19): merge especulativo + análise de conflito via build-graph, milhares de commits/dia com main sempre verde. Nosso AC em produção já é essa primitiva.

modelo validado

jj prova a adoção; nós somos o forge que falta

Jujutsu: 27k stars, financiado pelo Google, conflitos first-class, change-ids — e explicitamente sem forge nativo. Mesma data-model do git, interface nova: a comunidade aceita repensar o workflow desde que o git fique intacto. Exatamente nossa tese.

2 · O que já está em produção hoje (CoreLink, ~71 crates Rust, Cloudflare)

  • CAS multi-região R2 — chunking (SplitBlob/SpliceBlob), manifests Merkle, multipart
  • Action Cache memoizado + superfícies Bazel REAPI v2, Turborepo, sccache (WebDAV) — multi-toolchain desde já

3 · O genuinamente novo — e por que acreditamos em cada peça

⛓️Refs transacionais por repo

Durable Object por repositório = serialização natural de refs com consistência forte, sem coordenador global. O event-log do forge É o ref-store (undo universal cai de graça). Throughput de um repo quente: lote de updates por DO — o mesmo padrão dos nossos DOs de billing.

🔭Merge especulativo contínuo

Blueprint do SubmitQueue + nossa vantagem: o orquestrador declara o DAG e as claims, então o espaço de busca de conflitos é dirigido, não cego. Conflito textual via merge incremental; semântico via build-graph (REAPI já nos dá targets).

🗺️Índice semântico incremental

Memoizado por tree-hash como tudo aqui: re-indexa só o delta de cada change. Tree-sitter para símbolos/AST (maturidade Mergiraf-class), build-graph para impacto. Não é embedding mágico — é indexação determinística + sumários LLM cacheados para sempre por hash.

🔐Cercas de capability

Workspace materializa SÓ as claims do WP (sparse por construção); secrets nunca entram — broker assina operações privilegiadas (modelo write-only de secrets da CF, generalizado). Atribuição por principal no event-log. É política enforced por física, não por boa vontade do agent.

4 · A física do moat (não é feature — é termodinâmica de custo)

Hidratação é a operação mais egress-pesada de um forge/sandbox. R2 tem egress zero; qualquer concorrente em S3 paga por byte servido — para sempre. Dedupe content-addressed: mil workspaces ≈ 1× repo + deltas. E o efeito de rede: artefato público determinístico é armazenado uma vez e aquece o cache de todos — agora aplicado também a resultados de check. Concorrente sem escala não consegue nem o custo, nem o hit-rate.

Q1"Compatibilidade git é uma cauda infinita de edge cases. Vocês vão se afogar."
Por isso a escada começa estreita: smart-HTTP protocol v2 (negotiation + packfiles) — o subconjunto que clientes modernos usam — servido de uma implementação libgit2-class, não reescrita do zero. O fallback sempre existe: o mirror GitHub é a rota de escape durante a maturação. E o produto nº 1 (landing layer) nem precisa do protocolo — roda sobre o GitHub via API. A cauda longa é paga com receita, não com fé.
Q2"Merge resolvido por LLM vai alucinar e corromper código silenciosamente."
Três camadas ANTES do LLM: regeneração de arquivos derivados (mata a classe nº 1 medida), merge estrutural AST, e só então arbitragem LLM atrás de confidence gate — e a resolução vira uma Change revisável que passa pelos mesmos checks memoizados de qualquer change. Auto-merge errado não chega à main: a união é testada especulativamente antes de pousar. Pesquisa existe (ConGra: 44.948 conflitos benchmarkados); nós produtizamos com cinto e suspensório.
Q3"Cloudflare é single-vendor num caminho que agora é source-of-truth. Cache perdido se recomputa; repo perdido é catástrofe."
Reconhecido como o risco de classe mais alta — está escrito no brief (caveat #5). Mitigação tripla: (1) é tudo git — export full-fidelity contínuo + mirror GitHub como réplica viva desde o dia 1; (2) replicação cross-bucket multi-região já existe no CoreLink; (3) escrow de snapshot em provedor independente para tiers pagos. A promessa de exit não é marketing — é o plano de DR.
Q4"Throughput: um monorepo quente com frota de 50 agents commitando a cada 30s."
Escritas de objetos são CAS — paralelas, sem contenção por natureza. O ponto quente são refs: DO por repo com batch de updates (50 agents ≈ centenas de ref-ops/min — ordens de magnitude abaixo do limite de um DO). Stacks e workspaces têm refs próprios (sharding natural). E o landing é uma fila: serializar o pouso é o produto, não o gargalo.
Q5"Por que a GitHub simplesmente não constrói isso?"
Eles estão tentando a camada de cima (Agent HQ) — mas as primitivas de baixo (Actions sem memoização, webhooks fire-and-forget, rate limits humanos, billing por minuto) são o modelo de negócio deles. Memoizar CI canibaliza receita de Actions; egress zero exige sair do próprio datacenter pricing. O CTO deles admitiu acoplamento arquitetural em cascata (257 incidentes/ano). Incumbente reconstrói fundação E canibaliza receita ao mesmo tempo? Essa aposta tem nome: Innovator's Dilemma.
